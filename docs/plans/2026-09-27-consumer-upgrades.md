# Consumer upgrade propagation: Issue #30

## Authorized target and sourced capability

Implement the user's release → discovery → proposal → verification → governed merge → explicit re-proof architecture without changing the frozen contract. Renovate owns scheduling, discovery and PR maintenance; native GitHub Issues, owner approvals, checks and rules remain authorities. No fleet registry or tracker is introduced.

## Design

Stable releases must be GitHub immutable releases with exact SemVer tags resolved to full commit SHAs. A release contains a declarative `openharness-release.json`, generated by the released compiler, with generated artifact content and explicit compatible source versions. Consumers store `.harness/installation.json`; runtime execution remains the SHA in the existing controller configuration. A separate upgrade request is Renovate's dependency input, never an execution ref.

A deterministic planner verifies release/tag/commit identity, compatibility and installed artifact hashes, changes only the controller SHA and compiler-owned artifacts, and preserves project configuration. Major transitions and pre-1.0 minor transitions stop. Apply validates all paths and inputs before writing, rolls back on write failure, and never activates. Doctor fingerprints the installation and rejects inconsistent artifacts or pins. The trusted baseline candidate controller validates the proposed installation delta independently, then runs old and new acceptance configurations through its existing sandbox.

Self-hosted Renovate uses an allowlisted post-upgrade command installed from the old trusted SHA. It prepares the declarative proposal without executing new release code. Its Issue-bound branch/body are configured against an existing open upgrade Issue; the existing owner control approval and sourced check are still required. Repository-local lifecycle commands retain their preflight. Bot proposal staging makes no claim to managed local activation.

## Implementation sequence

1. Add release/installation validation, immutable resolution, compatibility and transactional migration tests with real Git consumers.
2. Implement `openharness.updates` using standard library, native Git and existing GitHub API observation. Add release manifest and Renovate preset commands.
3. Connect optional release enrollment/staging to existing upgrade, installation validation to Doctor, and independent proposal validation to trusted candidate verification. Protect the new executed dependency in producer identity.
4. Add end-to-end detection, correct proposal, acceptance failure, mutable/untrusted rejection, migration repeatability, rollback, stale activation and explicit re-proof tests.
5. Run full unittest discovery and compileall, commit in the bound workspace, verify the exact candidate and observe Doctor. Open the Issue-bound PR with evidence and attach it.

## Evidence boundary

Fixture success does not establish live provider enforcement. Current repository has no published release. A published immutable release and configured self-hosted Renovate runner are explicit deployment prerequisites; enrollment fails until its release identity exists.
